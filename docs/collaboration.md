# 공통 작업 규칙

## 작업 위치

- `src/oinq/`는 공통 코드, `scripts/`는 실행 입구, `configs/`는 실행 조건이다. 노트북에만 존재하는 공유 로직을 만들지 않는다.
- 국가·제품·기간·변수는 YAML을 읽는다. API 키는 `.env`에서 읽고 YAML·로그·노트북 출력에 기록하지 않는다.
- 기존 문서·코드를 덮어쓰기 전에 변경사항을 확인하고 맡은 범위만 수정한다.

## Git 작업 권장 규칙

- 현재 기본 브랜치는 유지한다. 개인 작업은 `feature/<기능>` 또는 `fix/<문제>`처럼 목적별 브랜치에서 진행한다.
- 커밋은 `feat:`, `fix:`, `docs:`, `test:`, `chore:` 접두사와 실제 변경 내용으로 작성한다.
- 공통 설정·스키마·전처리 변경은 팀장 검토 후 합친다. 원격 push·PR 생성·merge는 팀의 지시에 따라 수행한다.
- 공유 전 `git diff --check`, `git status --short`, 설정 점검과 관련 테스트를 실행한다. 비어 있는 폴더는 필요한 경우 `.gitkeep`으로 보존한다.

## 데이터 변경

- 공통 데이터는 `data/shared/<version>/` 단위로 배포한다. 수정 시 새 버전을 만들고 컬럼·행 수·기간·출처·체크섬을 manifest에 기록한다.
- 데이터 파일이나 독립변수 변경을 모델 실험 폴더에서 조용히 덮어쓰지 않는다. 공통 전처리 변경 제안과 모델별 변환을 구분한다.
- 같은 검증 행·예측 기준일·예측 거리로 모델을 비교한다. 2026년 최종 테스트는 튜닝과 변수 선택에 사용하지 않는다.

## 환경과 결과

- Python 3.12.x와 `pyproject.toml`의 의존성을 사용한다. 설치 버전은 각 실험의 메타정보에 기록한다.
- `artifacts/<run_id>/`에 모델·전처리기·파라미터·변수 목록을 함께 보관한다. 용량이 큰 모델은 별도 인계하고 경로·체크섬을 남긴다.
- 공유 승인된 검증 보고서만 `reports/`에 넣는다. 원본·전체 가공 패널·개인 문서·최종 테스트 정답은 커밋하지 않는다.
- 팀원별 실명 배정과 세부 일정은 별도 협의한다. 이 문서는 개인 평가나 개인 운영 메모를 포함하지 않는다.
